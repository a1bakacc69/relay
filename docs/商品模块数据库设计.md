## 一、先搞清楚：商品在系统里怎么流动

这个项目里有**两条方向相反的流**，一开始就得分开：

```
商品流（正向）
  供应商（速卖通）──→ 我们（Relay）──→ 销售平台（Shopify）
     有货可卖            导入、加价、改标题      上架卖

订单流（反向）
  供应商（速卖通）←── 我们（Relay）←── 销售平台（Shopify）
       发货              转发 + 回写物流          买家下单
```

**为什么方向是反的**：商品从货源流向消费者眼前，订单从消费者流回货源。
同一条货，在两条流里是"逆向"的 —— 所以以后要有个东西把两头对上号（映射表，后面的阶段做）。

### 1.1 商品的三段链路

| 段 | 谁做 | 状态 |
|---|---|---|
| ① 供应商上架商品 | 供应商（`dsers-supplier` 模拟） | ✅ 已做完 |
| ② 我们导入并加工 | 我们 | 🚧 本次要做 |
| ③ 推到销售平台卖 | 我们 | ⬜ 还没做 |

### 1.2 ★ 最重要的一句话：供应商的货，不在我们的库里

| | 存在哪 | 怎么访问 |
|---|---|---|
| 供应商的商品 | `relay_supplier` 库（**他自己的库**） | 只能通过 HTTP 接口读 |
| 我们的商品 | `relay` 库（**我们的库**） | 直接读写 |

供应商的商品目录可能有几万条，我们**只会导入自己看中的那几条**。

把全量同步过来既没必要，也不现实 —— 真实的供应商不会让你直连他的数据库。

> **所以**：导入这个动作，本质是「**从对方接口要一份数据，在自家库里存一份副本**」。
> 存下来这份是**我们的**，可以随便加工；对方那份我们**一个字都改不了**。

## 二、两条必须记住的规则

### 规则 1 · 事实 vs 营销：这个字段谁说了算

商品字段比订单字段更容易搞混，因为**同一件货有两套价**。

判断方法只有一句话：**这个值，是我说了算，还是供应商说了算？**

| 字段 | 谁说了算 | 为什么 |
|---|---|---|
| `cost_price` 采购价 | **供应商** | 他卖给我多少钱就是多少钱 —— 这是**事实** |
| `stock` 库存 | **供应商** | 他有多少货，只有他知道 —— 这是**事实** |
| `sale_price` 售价 | **我们** | 我卖多少钱，我定 —— 这是**营销** |
| `title` 标题 | **我们** | 怎么写吸引买家，我定 —— 这是**营销** |

**记法**：

- **事实**（成本、库存）→ 供应商改了，我们**必须跟着变**，不跟就是错的
- **营销**（售价、标题）→ 供应商改了，我们**无脑不动**，跟着变就是灾难

> **当时真的这么想过，被否掉了**：
>
> 「设个 2 倍加价，售价自动跟着采购价浮动，多省事。」
>
> 供应商把采购价从 60 降到 **40** —— 你的售价**自动掉到 80**。
> 可你本来卖 120 卖得好好的，凭什么跟着降 33%？**利润直接被砍掉一半。**
>
> 所以：**采购价跟着供应商变，售价由我们自己定。两者必须分开存两个字段。**

这条规则和订单模块的「A/B/C 分区」**是同一个思路**，只是换了个场景：

| | 订单模块 | 商品模块 |
|---|---|---|
| 判断依据 | 数据从哪来 | 是事实还是营销 |
| 「跟着变」的 | A 区（平台镜像） | `cost_price`、`stock` |
| 「绝不碰」的 | B 区（自有业务） | `sale_price`、`title` |

> **写同步代码时**：SQL 里只出现 `cost_price`、`stock`。`sale_price` 和 `title` 一个都别提。

### 规则 2 · 幂等：拿供应商的商品 ID 当唯一键

和订单模块的 `uk_platform_order` 是**一模一样的思路**。

导入按钮点两次，库里应该还是**一条商品**，不是两条。

| 表 | 唯一键 | 防的是什么 |
|---|---|---|
| `products` | `uk_supplier_product(supplier_product_id)` | 同一个供应商商品被导入两次 |
| `product_variants` | `uk_supplier_variant(supplier_variant_id)` | 同一个供应商规格被导入两次 |

**但有一点和订单模块不同 —— 这里重要：**

| | 重复触发时怎么办 |
|---|---|
| **订单**重复拉取 | **刷新**它（A 区字段重新覆盖一遍） |
| **商品**重复导入 | **什么都不做**，直接说「这个导入过了」 |

**为什么不一样**：

商品的「变更」走的是**另一条路** —— 供应商改价、改库存、下架，
靠**同步**（webhook / 定时任务）推过来，**不是靠"再导一次"**。

- **导入** = 第一次搬运，搬完这条线就结束了
- **改价 / 改库存 / 下架** = 之后的变更，归同步管

如果导入接口也顺手更新，就会出现**两套逻辑做同一件事**，迟早对不上。

> 一句话：**导入只管"第一次"，之后的变更归同步管。**

## 三、`products` 表（我们的商品）

### 3.1 完整结构

```sql
CREATE TABLE `products` (
  -- ===== 识别一条商品 =====
  `id`                   bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `supplier_product_id`  bigint       NOT NULL COMMENT '★ 来源：供应商侧 supplier_products.id。导入幂等靠它',

  -- ===== 商品信息（营销数据，我们自己改） =====
  `title`                varchar(255) NOT NULL COMMENT '商品标题。导入时取自供应商，导入后可以改',
  `description`          text                  COMMENT '商品描述',
  `image_url`            varchar(500) DEFAULT NULL COMMENT '主图，只存外链，不做图片上传',
  `category`             varchar(64)  DEFAULT NULL COMMENT '类目',

  -- ===== 定价 =====
  `price_ratio`          decimal(5,2) DEFAULT NULL COMMENT '★ 加价倍数：售价 = 采购价 × 本值。2.00 = 卖两倍价。NULL 表示还没定价',

  -- ===== 状态 =====
  `status`               varchar(20)  NOT NULL DEFAULT 'DRAFT' COMMENT 'DRAFT 已导入未定价 / ON_SALE 在售 / OFF_SHELF 已下架',

  -- ===== 本地系统字段 =====
  `create_time`          datetime     DEFAULT CURRENT_TIMESTAMP COMMENT '本地创建时间',
  `update_time`          datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '本地更新时间',

  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_supplier_product` (`supplier_product_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='我们的商品表';
```

### 3.2 字段逐个说明

#### ▌ `id` ★ — 我们自己的商品主键

普通的自增主键，本地唯一。

**注意区别**：订单表的 `id` 会当幂等键**传给供应商**，商品表的 `id` **目前不传出去**。
传出去的是 `supplier_product_id`（往上游传）和以后的 `platform_product_id`（往下游传）。

#### ▌ `supplier_product_id` ★★★ — 这条货是从哪来的

| | |
|---|---|
| **是什么** | 供应商侧 `supplier_products.id` |
| **谁生成** | **供应商**（不是我们） |
| **什么时候写** | 导入时写一次，之后**永不修改** |

**三个作用**：

1. **导入幂等** —— 唯一索引靠它挡重复（规则 2）
2. **回去问最新数据** —— 想知道供应商现在卖多少钱，拿它去调 `GET /supplier/products/{id}`
3. **追溯** —— 出问题时能说清「这条商品抄的是哪一家的哪一条」

> ⚠️ 它**不是外键**。供应商的库不在我们这，跨系统建不了外键约束。
> 它只是个「引用地址」。对方下架了商品，我们这边**不会自动知道** —— 这是**有意的**，见 7.5。

#### ▌ `title` ★ — 商品标题

| | |
|---|---|
| **谁说了算** | **我们** |
| **导入时** | 从供应商那边抄一份，作为起点 |
| **导入后** | **随便改**，改完不会被任何逻辑覆盖 |

**为什么导入后还能改**：供应商的标题是给同行看的（"Wireless Bluetooth Earbuds Pro"），
你的买家在 Shopify 上看到的标题要按你自己的关键词写。**这是营销，归你。**

#### ▌ `price_ratio` ★★★ — 加价倍数

| | |
|---|---|
| **是什么** | 售价 = 采购价 × 这个数 |
| **谁说了算** | **我们** |
| **取值范围** | `decimal(5,2)`，最大 999.99 |

**为什么放在商品表，不放在规格表**：

一条商品的所有规格，通常用**同一个倍数**（保温杯 500ml 卖 2 倍，750ml 也卖 2 倍）。
放商品表 = 设一次全生效；放规格表 = 每个规格设一遍，麻烦还容易漏。

> **想给某个规格单独定价怎么办**：直接改那个规格的 `sale_price`。
> 倍数只是「批量算一遍」的工具，**算完的结果存在规格上**，之后以存的结果为准。

**为什么用倍数（2.00）不用百分比（200）**：

乘法更直观 —— `45 × 2 = 90`。
用百分比就要写 `45 × (1 + 100%)`，白多一层换算，没有任何好处。

**`NULL` 表示还没定价**：刚导入的商品没设倍数，算不出售价，
所以 `sale_price` 也是 `NULL`，商品停在 `DRAFT` 状态，不会被推出去卖。

#### ▌ `status` ★★★ — 三个状态的业务含义

| 值 | 含义 | 什么时候进入 |
|---|---|---|
| `DRAFT` | 已导入，**还没定价** | 导入后的默认状态 |
| `ON_SALE` | 在售，**可以推到销售平台** | 定完价之后 |
| `OFF_SHELF` | 已下架 | 不卖了 |

**为什么导入后不直接 `ON_SALE`**：

刚导入的商品**还不知道卖多少钱**（`sale_price` 是 `NULL`）。
这时候当成「在售」推出去，就是**零元卖货**。

所以默认 `DRAFT`，**逼你定完价才能上架**。

> 和订单表的 `status` 一个思路：**状态是业务代码说了算的，外部数据不许覆盖。**

#### ▌ `image_url` / `description` / `category`

这三个都是**营销数据**（我们说了算），但现阶段**还没有加工界面**，
所以实际表现是「导入时抄一份，暂时不动」。

以后加了编辑功能，改的就是它们。

#### ▌ `create_time` / `update_time`

C 区（本地系统字段），数据库自动维护，和订单表一样，业务代码不用管。

### 3.3 索引

| 索引 | 类型 | 作用 |
|---|---|---|
| `PRIMARY KEY (id)` | 主键 | 按我们自己的 ID 查 |
| `uk_supplier_product (supplier_product_id)` | **唯一** | ★ 导入幂等 |

**为什么 `supplier_product_id` 要唯一，而不只是普通索引**：

唯一索引是**数据库层面**的兜底。就算代码写错了、并发导入了两遍，
数据库也会直接报 `Duplicate entry`，**脏数据根本进不来**。

> 这和订单表 `uk_platform_order` 的道理完全一样 —— **约定会忘，约束不会。**

## 四、`product_variants` 表（我们的规格）

**为什么商品要拆成两张表**：一条商品有多个规格（500ml / 750ml / 1000ml），
买家下单买的是**具体规格**，不是"那个商品"。价格、以后要推给平台的库存，都是**规格级**的。
一条商品的规格数量不定，塞进 `products` 表里就得用 JSON 或逗号拼串 —— 那样查不了也改不动。

### 4.1 完整结构

```sql
CREATE TABLE `product_variants` (
  -- ===== 归属 =====
  `id`                   bigint        NOT NULL AUTO_INCREMENT COMMENT '主键',
  `product_id`           bigint        NOT NULL COMMENT '所属商品，关联 products.id',

  -- ===== 来源 =====
  `supplier_variant_id`  bigint        NOT NULL COMMENT '★ 来源：供应商侧 supplier_product_variants.id。下单给供应商时传的就是它',

  -- ===== 规格信息 =====
  `variant_title`        varchar(200)  NOT NULL COMMENT '规格名，如 Black / 750ml',
  `sku`                  varchar(50)   DEFAULT NULL COMMENT '供应商的货号，原样存着备查。和我们的 SKU 不是一回事',
  `image_url`            varchar(500)  DEFAULT NULL COMMENT '规格图，没有就沿用商品主图',

  -- ===== 两套价 ★ =====
  `cost_price`           decimal(10,2) NOT NULL COMMENT '★ A 区：采购价，来自供应商。供应商调价时同步逻辑可以覆盖它',
  `sale_price`           decimal(10,2) DEFAULT NULL COMMENT '★ B 区：售价，我们自己定。= 采购价 × products.price_ratio。同步逻辑永远不碰',

  -- ===== 本地系统字段 =====
  `create_time`          datetime      DEFAULT CURRENT_TIMESTAMP COMMENT '本地创建时间',
  `update_time`          datetime      DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '本地更新时间',

  PRIMARY KEY (`id`),
  KEY `idx_product_id` (`product_id`),
  UNIQUE KEY `uk_supplier_variant` (`supplier_variant_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='我们的商品规格表';
```

### 4.2 字段逐个说明

#### ▌ `id` — 规格主键

本地自增，用于订单明细、映射表以后引用它。

#### ▌ `product_id` ★ — 归属哪条商品

普通索引，不加外键（理由见 7.6，和订单明细的 `order_id` 一样）。

#### ▌ `supplier_variant_id` ★★★ — 这条规格在供应商那边的 ID

| | |
|---|---|
| **是什么** | 供应商侧 `supplier_product_variants.id` |
| **谁生成** | **供应商** |
| **★ 什么时候用** | **下单给供应商时，传的就是它** |

**为什么它比 `product_id` 还重要**：

以后订单模块改造时，「该给供应商下哪个货」这个判断，
靠的就是订单里的平台变体 → **找到这条记录** → 拿到 `supplier_variant_id` 传过去。

传错了，供应商会发错货（买家要 750ml，发成 500ml）。

所以它上面**也必须有唯一索引** —— 一个供应商规格在我们的库里只能对应一条记录，
不然映射的时候就不知道听谁的。

> ⚠️ 注意：**这条规格的供应商 ID，不等于它所属商品的供应商 ID。**
> 两个 ID 是两层的：`supplier_product_id` 管"哪条货"，`supplier_variant_id` 管"哪个规格"。
> 下单只认后者。

#### ▌ `variant_title` — 规格名

如 `500ml` / `Black`。导入时抄供应商的，**目前不给改**（改规格名会牵连平台上的 SKU，属于以后的活）。

#### ▌ `sku` ★ — 供应商自己的货号，原样存一份

| | |
|---|---|
| **是什么** | 供应商内部的货号，如 `BTL-750` |
| **谁生成** | 供应商 |
| **我们拿它干嘛** | **只是留着备查**，比如对账、跟供应商吵的时候 |

**为什么原样存，而不是用它当主键**：

- 它是**供应商**的编码规则，他随时可以改，改了我们的历史数据就断了
- 我们自己以后也会有 SKU（推给销售平台时用），**两套编码不是一回事**，混用会出事

> 存一份**不改不查**的副本，是为了出问题时能拿原话对质。

#### ▌ `cost_price` ★★★ — 采购价（A 区）

| | |
|---|---|
| **谁说了算** | **供应商** |
| **导入时** | 从供应商接口拿到，写进来 |
| **供应商改价后** | **同步逻辑覆盖它** |
| **能改吗** | 我们能改，但**改了没意义** —— 下次同步会被刷回去 |

对应供应商侧的 `supplier_product_variants.price`。

**为什么 `NOT NULL`**：采购价是**事实**，供应商那边一定有一个值（哪怕是 0）。
拿不到就是接口出了问题，不该静默存成空。

#### ▌ `sale_price` ★★★ — 售价（B 区）

| | |
|---|---|
| **谁说了算** | **我们** |
| **怎么算出来** | `= cost_price × products.price_ratio` |
| **谁能写** | **只有定价接口** |
| **同步逻辑** | **永远不碰** |

**★ 为什么必须落库存下来，而不是每次要用时现算**：

因为**历史订单的售价不能被改写**。

假设今天售价 90，买家下单了。下个月供应商涨价，`cost_price` 从 45 变成 60。
如果售价是"现算"的，那笔**上个月的老订单**回头一查，单价变成了 120 —— 但人家当时付的就是 90。

**账对不上了，而且是历史数据被篡改，查都没法查。**

所以：**算一次，存下来，以后以存的为准。**
改价只影响**之后**的定价，不影响**已经发生**的订单。

#### ▌ `image_url` — 规格图

没有就沿用商品主图。这是**展示逻辑**，不在库里做冗余。

#### ▌ 时间字段

C 区，同上。

### 4.3 索引

| 索引 | 类型 | 作用 |
|---|---|---|
| `PRIMARY KEY (id)` | 主键 | 订单明细、映射表引用 |
| `idx_product_id (product_id)` | 普通 | 按商品查它的全部规格（详情页、导入） |
| `uk_supplier_variant (supplier_variant_id)` | **唯一** | ★ 导入幂等 + 下单时精确定位 |

## 五、导入数据流

导入是这个模块唯一的**写入口**。走一遍：

```
① 用户在供应商商品列表里点「导入」
        │
        │  GET http://localhost:8081/supplier/products/{id}
        ▼
② 供应商返回：商品信息 + 变体数组（每个变体带 price / stock）
        │
        ▼
③ 先查 products：这个 supplier_product_id 导过没有？
        │
        ├── 导过 → 直接返回「已导入」，不做任何写操作 ★
        │
        └── 没导过
                │
                ▼
        ④ INSERT products        （title 抄供应商，price_ratio / sale_price 留空）
                │
                ▼
        ⑤ 拿到新商品的 id，逐个 INSERT product_variants
           （cost_price 抄供应商的 price，sale_price 留 NULL）
                │
                ▼
        ⑥ 商品状态 = DRAFT（还没定价，不能卖）
```

**几个必须记住的点**：

| 点 | 说明 |
|---|---|
| **③ 先查后插** | 唯一索引是兜底，正常路径靠先查。不要指望异常来控制流程 |
| **④ 一次导入写两张表** | 商品和规格必须一起写。只写了商品、没写规格 = 一条卖不出去的废数据 |
| **⑤ `cost_price` 抄的是 `price`** | 供应商接口里这个字段叫 `price`，含义是"采购价"。**别直接当成售价** |
| **`stock` 没有落库** | 现在我们的表里**没有库存字段** —— 这是个已知缺口，见第六章 |
| **`sale_price` 留 NULL** | 导入时**不算价**。定价是下一步的独立动作 |

### 5.1 导入之后发生什么（定价）

```
PUT /products/{id}/pricing   { "priceRatio": 2.0 }
        │
        ▼
① 更新 products.price_ratio = 2.0
        │
        ▼
② 查这条商品的全部规格
        │
        ▼
③ 逐个算：sale_price = cost_price × 2.0，写进 product_variants
        │
        ▼
④ products.status = ON_SALE
```

**为什么定价要单独一个接口，不塞进导入里**：

因为**导入是一个动作，定价是另一个决策**。
有些商品导进来就是先囤着看看，不一定马上卖。
硬把两件事绑在一起，等于逼用户"要么别导，要么立刻定价"。

## 六、★ 已知缺口：库存没有落库

**这是本次写文档时发现的，先记在这里，别装作没看见。**

供应商侧的 `supplier_product_variants` 有 `stock` 字段（而且种子数据里故意留了两条 `stock = 0`
用来测断货），但**我们这边的 `product_variants` 没有**。

**这意味着什么**：

现在能算出「卖多少钱」，但算不出「还剩几件」。
以后要把商品推到销售平台时，平台会问你要库存 —— 到时候这条路是断的。

**但不能拍脑袋马上加，有两个问题要先想清楚**：

1. **存还是不存** —— 库存是**事实**（供应商说了算），而且是**高频变化**的。
   存一份就是存了个**缓存**，随时可能过期。那到底是每次要用时实时去问供应商，还是存一份快照？
2. **下单时怎么办** —— 就算存了快照，买家下单那一刻供应商可能已经卖完了。
   **下单给供应商之前是不是必须实时验一次库存？**

> 这两个问题在**阶段 3（下单链路改造）**的时候会正面撞上，
> 到时候再定。现在先知道"有这么个坑"就够。

## 七、为什么这么设计（防止你改错）

### 7.1 为什么不直接用供应商的商品，非要各存一份

**因为要加工**：

- 改标题、换图、改描述（营销）
- 加价（卖 2 倍）
- 挑着导入（几万条里只导几条）

供应商那份是**原料**，我们这份是**成品**。原料你改不了（在人家库里），成品是你的。

### 7.2 为什么 `cost_price` 和 `sale_price` 要用两个字段

一句话：**这两个数会分叉。**

- 采购价供应商说变就变，我们必须跟
- 售价是我们定的，供应商无权干涉

**合成一个字段**会怎样：要么售价被迫跟着供应商跑（利润被砍），
要么采购价不跟（算利润的时候用的是假数据）。**怎么都是错的。**

### 7.3 为什么 `sale_price` 要落库，不查询时现算

见 4.2 里那段 —— **历史订单的售价不能被改写**。

现算的代价是：供应商一涨价，所有历史订单的"单价"跟着变，账全乱。

### 7.4 为什么 `price_ratio` 在商品表，不在规格表

同一条货的规格通常共用一个倍数，放商品表设一次全生效。
放规格表要设 N 遍，**改的时候漏一个就出现"同一条货两个价"**。

### 7.5 为什么 `supplier_product_id` 不做外键

**跨系统建不了外键** —— 供应商的库在另一台机器、另一个进程里，MySQL 管不着。

而且**有意不追求强一致**：供应商下架了商品，我们这边不会自动知道，
这是**正常的**（以后靠同步机制感知，不靠数据库约束）。

> 外键只能约束**同一个库**里的表。`product_variants.product_id` 理论上能加外键，
> 但我们**统一都不加** —— 理由和订单模块一样：加了外键，删数据时要考虑顺序，
> 批量操作和分库分表都会变麻烦，**一致性靠代码保证，不靠数据库**。

### 7.6 为什么商品和规格拆两张表

**规格数量不定**。一条货 3 个规格，另一条 20 个。

塞一张表就得用 JSON 或逗号拼串 —— 那样**既查不了（没法 `WHERE 价格 > 50`）也改不动**（改一个规格要读出来改完再写回去）。

拆开之后，每个规格是一行，标准的做法。

### 7.7 为什么 `sku` 要原样存一份

见 4.2 —— 供应商的编码他会改，而且**和我们自己的 SKU 不是一回事**，
混用会让"到底该发哪个货"变成罗生门。存一份只读的副本备查。

### 7.8 为什么「导入」和「同步」是两件事

**防的是"两套逻辑写同一批数据"**。

- 导入：只在**第一次**写，之后再不碰
- 同步：负责**之后的变更**（改价、改库存、下架）

如果导入也顺便更新，那供应商改了价之后，**到底以哪次导入的为准**就说不清了。
职责分清楚，出问题才知道该查哪。

## 八、说好不做的（别被带跑）

| 不做 | 原因 |
|---|---|
| ❌ 图片上传 / 存储 | 只存外链。做图床是另一个工程，和"同步"这个核心价值无关 |
| ❌ 供应商商品全量同步 | 几万条，没必要也做不到。**按需导入** |
| ❌ 一条供应商商品导入成多条我们的商品 | 唯一索引挡着。想让一条货在两个店卖不同价，那是**映射层**的活 |
| ❌ 在商品表里存库存 | 见第六章 —— 不是不做，是**要先想清楚**，阶段 3 再定 |
| ❌ 规格级的独立加价倍数 | 一个商品一个倍数，单个规格要特殊价就直接改 `sale_price` |
| ❌ 编辑供应商商品 | 我们**没有写权限**，对方也没开这个接口。中台只能看上游 |

## 九、速查表

### 9.1 字段 → 谁说了算

| 字段 | 表 | 谁说了算 | 同步能覆盖吗 |
|---|---|---|---|
| `cost_price` | `product_variants` | 供应商 | ✅ 能，而且应该 |
| `title` | `products` | 我们 | ❌ 不碰 |
| `sale_price` | `product_variants` | 我们 | ❌ 不碰 |
| `price_ratio` | `products` | 我们 | ❌ 不碰 |
| `status` | `products` | 我们 | ❌ 不碰 |
| `sku` | `product_variants` | 供应商 | 只读副本，不参与逻辑 |

### 9.2 两个 ID 别搞混

| ID | 存在哪 | 指向 | 用在哪 |
|---|---|---|---|
| `supplier_product_id` | `products` | 供应商那边**哪条货** | 导入幂等、回去查最新数据 |
| `supplier_variant_id` | `product_variants` | 供应商那边**哪个规格** | ★ **下单给供应商时传的就是它** |

> 一句话：**商品级用来看，规格级用来下单。**

### 9.3 状态机

```
DRAFT ──定价──→ ON_SALE ──下架──→ OFF_SHELF
（刚导入）                  （在售）              （不卖了）
```

### 9.4 三对容易混的

| 看着像一回事 | 实际区别 |
|---|---|
| `cost_price` vs `sale_price` | 前者是事实（供应商定），后者是营销（我们定）。**永远不同步** |
| `supplier_variant_id` vs `sku` | 前者是 ID（机器用，下单传它），后者是货号（人看，备查） |
| `supplier_product_id` vs `supplier_variant_id` | 一个是"哪条货"，一个是"哪个规格"。**下单只认规格** |
